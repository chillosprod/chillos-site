Developer framework

Build with ChillOS,
not over it.

DKER 3.0 and the public source tree are open to exploration. This guide explains what is welcomed, what must remain attributed and what the project will not accept.

AllowedRequiredNot allowedContributingBrandingDMCA policy
01 · Allowed

Use the framework to make real things.

Apache License 2.0 permits broad use, modification and redistribution when its conditions are respected.

Study and modify the source

You may inspect architecture, change modules, create experiments and maintain private forks.

Build DKER 3.0 applications

Create original applications, modules, themes and integrations that use documented ChillOS APIs.

Redistribute compliant derivatives

You may distribute source or object versions when recipients receive the Apache 2.0 license, changed files are clearly marked and required notices are retained.

Describe compatibility honestly

You may say that a product is “compatible with ChillOS” or “built with DKER 3.0” when the statement is accurate and does not imply official endorsement.

02 · Required

Keep the history attached to the code.

A permissive license is not a permission to erase authorship.

  1. Include the Apache License 2.0 text.Recipients of the work or a derivative work must receive a copy of the license.
  2. Mark modified files prominently.Do not present a changed copy as an untouched official ChillOS release.
  3. Retain relevant notices.Keep copyright, patent, trademark and attribution notices that apply to the redistributed source.
  4. Preserve NOTICE information when present.If the distributed work includes a NOTICE file, reproduce the required attribution information in a readable place.
  5. Separate your promises from the project.Any warranty, paid support or additional liability you offer is yours, not the ChillOS team’s.
Source of truth: the repository license and the complete Terms of Use control over this plain-language summary.
03 · Not allowed

Do not erase, impersonate or weaponize.

These actions conflict with the project terms, the license, or the safety boundary of the product.

Removing ownership and license notices

Do not strip copyright information, attribution, license text or applicable NOTICE material from redistributed copies.

Claiming an unofficial build is official

Do not present a fork, modified binary or third-party service as an official ChillOS release or as work authored by the original team.

Using project names as your commercial identity

ChillOS, INMORE, PCHLLKernel and Atlanta may not be used as the name or branding of an unrelated commercial product without written permission.

Malware, spyware and unauthorized surveillance

Do not use the framework or built-in tools to distribute harmful code, collect data without authorization or mislead users about system behavior.

Safety-critical deployment

Do not use ChillOS in medical, life-support, critical infrastructure or other systems where failure could cause injury or death.

04 · Contributions

Make changes reviewable.

A good contribution explains not only what changed, but why it belongs in the system.

  1. Start from a focused issue.Describe the behavior, expected result, affected module and reproduction steps.
  2. Keep localization centralized.No user-facing string should be hard-coded inside a screen or application when a locale key can be used.
  3. Respect the virtual-disk boundary.Applications must not run arbitrary host commands or access host data outside explicitly approved integration points.
  4. Add tests for state changes.Language switching, app open/close cycles, formatting, OOBE and recovery paths must not silently reset preferences.
  5. Document visual and API changes.Include screenshots when useful and list any compatibility break clearly.
05 · Branding

Compatibility is not endorsement.

The code license does not grant a general trademark license.

Reasonable attribution

“Based on ChillOS Python Core” and “Compatible with DKER 3.0” are acceptable when true and visually secondary to your own product name.

Logos and graphical assets

Use original project graphics only where the license and Terms permit. Do not modify a logo in a way that suggests a new official edition.

False affiliation

Do not use “official”, “certified”, “partner” or similar wording without written approval from the ChillOS lead developer.

Need a decision? Contact Alexander Tihomirov before publishing ambiguous commercial branding.

Questions before release?

Ask first when licensing, branding or redistribution is unclear.
